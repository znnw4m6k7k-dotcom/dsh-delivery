# 交付工具包改进任务：第一批

你在改 `~/Claude逆向工程/dsh-delivery-repo/kit`（交付工具包源码）。规则：
- 只改这个目录，不改 DSH 应用本身。
- 每项改完跑 `cd ~/Claude逆向工程/dsh-delivery-repo/kit && node --test tests/*.test.mjs`，全部通过才算完成。
- 新功能必须带单元测试，测试要有真实断言。
- 不删已有测试，不改已有测试的断言来凑通过。
- 风格跟现有代码一致：纯 JS（ESM），无依赖，注释用中文。
- 做完一项，在本文件末尾的“进度”里记一行：改了哪些文件、加了哪些测试。

相关文件：
- `bundle/index.js`：Host 插件（守卫规则 R1–R5、证据 E1、只读路由、斜杠命令）
- `bundle/workbench/state.mjs`：工作台数据
- `bundle/client.js`：面板
- `skills/delivery-protocol/SKILL.md`：交付协议
- `tests/`：测试

## 1. 测试证据计数（E1 增强）
- 在 `tools/result` 记录证据时，从输出里解析通过数和失败数，写进 evidence.jsonl 的 `tests: {passed, failed, total}`。
- 至少支持这几种格式：
  - node --test：`# pass N` / `# fail N`
  - pytest：`N passed, M failed`
  - unittest：`Ran N tests` + `OK` / `FAILED (failures=M, errors=K)`
  - go test：`ok` / `FAIL` 行，以及 `--- PASS/FAIL`
  - jest / vitest：`Tests: N passed, M failed, T total`
- 解析不出来时写 `tests: null`，同时写 `count_unconfirmed: true`。
- 区分验收运行和排查运行：
  - 命令在 freeze.json 的 test_commands 里，记 `purpose: "delivery"`。
  - 其他测试类命令（`node -e`、`echo`、单个文件的 `node --check` 等），即使也被记录，也一律记 `purpose: "diagnostic"`，永远不算验收。
- 解析函数单独导出（比如 `parseTestCounts(output)`），每种格式至少一个测试。

## 2. 原样重跑拦截（新规则 R6）
- 在 `tools/pre-execute` 里检查：要运行的是冻结的测试命令，而 evidence.jsonl 里**同一冻结版本、同一命令、同一角色**（main 或 subagent，沿用证据里的 agent 字段）已经有一条 `purpose: "delivery"` 的记录。按角色区分，是为了不挡住 QA 子 Agent 自己跑一遍。冻结期间文件不能改（R1），所以再跑一次结果不会变，这种情况直接拒绝。
- 拒绝信息给模型看，意思是：同一版本的同一测试已经跑过、结果不会变，先改代码并重新冻结；如果确实只是环境问题，就在命令前加注释 `# retry_reason: ...` 再跑。
- 带 `# retry_reason:` 的命令放行，并在证据里记下这个原因。
- 测试要覆盖四种情况：第一次放行、同角色原样第二次拦截、主 Agent 跑过之后 QA 子 Agent 第一次放行、带原因放行。

## 3. QA 等待验收期间只读（R3 加强）
- 冻结后等待验收期间（当前冻结版本还没有 QA 结论），**子 Agent** 只能写 `.delivery/qa/` 下的文件，写其他任何文件都拒绝。主 Agent 的行为不变（R1 已经保护冻结文件）。
- 判断是不是子 Agent，沿用现有的 isRoot 判断。
- 加测试。

## 4. 守卫拒绝说人话
- 每条拒绝信息保留现在给模型看的部分，后面另起一行，加一句给用户看的说明，格式固定：
  `【给你的说明】……`
- 说明要讲清楚：这是正常的保护还是流程出了错，以及用户需不需要做什么。大部分情况下用户什么都不用做，Agent 会自己调整。
- 每条规则（R1–R6）都要有这句说明，测试检查每条拒绝信息里都有 `【给你的说明】`。

## 5. 工作台显示“当前卡在哪”
- 在 `state.mjs` 的结果里加 `next: {who: "user"|"agent"|"qa"|"none", text: "一句话"}`，根据阶段推断。例如：
  - 合同还没确认：等你确认验收条目
  - 已冻结、没有 QA：等 QA 验收 vN
  - QA 不通过：Agent 在修第 K 轮
  - 已交付：可以做复盘
- 再加两个字段：
  - `rework`：返工轮数，等于 QA 不通过的版本数。
  - `evidence.currentVersion` 里的 `passed` / `failed` / `unconfirmed`：本版本最近一次验收运行的计数。
- 面板顶部用一行醒目文字显示 `next.text`。返工达到 3 轮或以上时，这一行标红，后面加“建议停下来和用户确认范围”。KPI 区加一格“测试”，显示 passed/total，未确认时显示“数量未确认”。
- `render.mjs` 的 HTML 也显示同样的信息。
- 加测试。

## 6. 自检命令 /delivery-doctor
- 在 `index.js` 里注册斜杠命令 `delivery-doctor`（跟 `delivery-workbench` 一样，用 commands 服务），返回中文检查结果，每行格式为“✓ 项目：说明”或“✗ 项目：怎么修”。检查以下各项：
  1. 插件版本：读 package.json 的 version。
  2. 守卫是否加载：命令能运行就说明加载了。
  3. 技能目录：`<工具包目录>/skills/` 下的 delivery-protocol、delivery-intake、independent-qa、industry-learning、project-retro 是否都在。
  4. 当前会话的工作目录，以及工作区里找到了哪些交付项目（复用 `listDeliveryProjects`）。
  5. 每个项目的 `.delivery/` 关键文件能否正常解析（contract.json、freeze.json、qa/*.json）；坏掉的 JSON 要指出文件名。
  6. 行业经验包：`~/.agents/skills/industry-*` 有几个，各自的版本号。
- 检查逻辑写成可测试的纯函数，比如 `doctorReport({kitDir, cwd, home})`，加测试。
- 在 `skills/delivery-protocol/SKILL.md` 里加一句：用户说“检查一下交付工具 / 好像不灵了”时，提醒用户输入 /delivery-doctor。
